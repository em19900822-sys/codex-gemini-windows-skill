# 代理端口变化：故障证据、恢复与自动跟随

适用：曾经可以聊天，重启网络代理后又出现 GPT 502，或 Gemini 的 Google 授权刷新 503。以下端口来自 2026-09-22 的一次本机故障，是证据，不是办公室电脑应照抄的配置。

## 这次发生了什么

| 观察项 | 本机证据 |
| --- | --- |
| 用户报错 | GPT 曾报 `OpenAI upstream is unreachable`；本次 Gemini 报 `Token refresh failed`、`client error (Connect)`，无法连接 Google 授权服务器 |
| 当前网络代理 | Windows 系统代理为 `127.0.0.1:23054`，当前代理进程在该端口监听 |
| 模型后台 | 网关与 Antigravity 后台在前一天启动，实际进程的 `HTTP_PROXY`、`HTTPS_PROXY` 仍为 `http://127.0.0.1:21761` |
| 旧代理地址 | `21761` 已无监听，后台继续连接旧地址 |
| 新代理连通性 | 无认证请求 Google 授权端点返回 404，OpenAI 端点返回 401；两者只证明网络连接可达，不代表账号验证成功 |
| 恢复 | 使用当前系统代理重新启动已确认身份的两项后台，再做真实模型回复测试 |

明确因果链：代理重启改变地址 → 长期运行的后台保留旧代理环境 → 无法连接上游 → Gemini 登录续期请求发不出去，或 GPT 返回连接错误。

这与“开机时后台先于代理启动”是不同触发条件。开机等待器成功启动服务后如果退出，就不会处理使用途中地址变化。用户已经先连代理再打开 Codex，也仍可能遇到此问题。

## 排查：先证明地址不一致

1. 确认截图报错发生在正在检查的电脑；`127.0.0.1` 指向该电脑本身。
2. 读取当前用户 Internet Settings 的 `ProxyEnable`、`ProxyServer`，核对实际监听进程和启动时间。不要打印代理软件的整份配置。
3. 对本机网关和 Antigravity 端口查 PID、可执行路径、命令参数、创建时间；区分“权限不足”与“服务不存在”。不能只看进程名字。
4. 比较服务实际使用的代理地址与系统代理。**当前终端的环境变量不能代表昨天已经启动的后台。** 优先用应用诊断、已记录的启动状态或受支持接口。若必须做进程级只读检查，只提取网络代理变量，不导出完整环境、内存、令牌或账号资料。
5. 用新代理分别检查 Google 授权端点与 OpenAI 服务的 HTTPS 连通性。请求不携带 Cookie、Authorization 或刷新令牌；保留状态码/异常类型，不保留响应正文。
6. 新代理也无法连通时，先处理网络代理本身；不要反复重启模型服务。若地址相同、端口正常，应继续检查实际异常，不套用本次结论。

`/health` 返回 200 仅说明本机服务还活着。`Connect` 错误不等于账号失效；`Token acquisition timeout` 的文字也不等于已检测到死锁。不要据此删账号、改用付费 API 或重新安装。

## 恢复：刷新已确认后台的连接

前提：新代理已经可用，登录与模型配置仍正确。记录实际服务 PID、创建时间和相关配置文件哈希，备份本次需要改动的启动脚本；不复制认证文件到公开材料。

1. 先检查目标电脑是否存在另一套付费 API 配置；没有明确授权，不切换到该连接。保留原 ChatGPT 登录。
2. 只停止身份已经核对的后台进程。网关可能有 venv 启动进程与基础 Python 子进程，分别核对路径和参数；停止前再次确认 PID 与创建时间，处理子进程退出后父进程自然退出的情况。不批量结束 Python、Codex、网络代理或其他程序。
3. 等待旧服务释放端口；未知进程占用或超时就停止继续启动并报告，不强杀占用者。
4. 用目标电脑已验证的启动器重新启动后台。必须在新进程中把 `HTTP_PROXY`、`HTTPS_PROXY` 刷新为**当前**代理，不能只在变量为空时设置。合并保留 `NO_PROXY` 中已有例外和本机地址；不修改用户全局代理、账号或模型目录。
5. 后台窗口保持隐藏。启动器退出后，再确认两项服务仍存活并通过本机健康检查。
6. 在生成测试前检查网关报告的 GPT 上游为 `codex_oauth`。说明会使用少量现有账号额度，分别通过 Codex 后台协议测试用户实际使用的 GPT 与 Gemini，检查正常文本和 completed 状态。
7. 请用户在原来报错的桌面任务重发消息；是否需要新任务要由提供商绑定决定，不一概要求重装或重开电脑。

仓库 `scripts/Start-Bridge.ps1` 会刷新启动子进程的代理变量，并在退出时恢复调用者的变量。它只负责单次启动，已有网关占用时会保留现状并报错；不能把它当作一键重启脚本。

## 按需自动跟随：用户不需要增加操作

用户要求“开机后先连代理，再手动打开 Codex，后台自动准备”时，可在目标电脑已有、审查过的后台启动器上补充以下逻辑。**不要因一次故障就默认安装常驻监控，也不要改动 Codex 窗口自启动、节点选择或其他应用设置。**

```text
本次登录的单实例后台
  等待系统代理就绪
  启动已验证的模型后台，记住这次实际使用的代理地址
  每 15 秒只读取一次本机系统代理设置
    关闭、未就绪或地址未变：不重启、不发模型请求
    地址变化：确认新代理可达，并再次核对地址没有继续变化
      调用已审查的恢复程序，重新核对待重启进程的身份
      健康检查通过后更新已使用地址
      失败时保留旧状态、退避再检查；未知占用、配置冲突或权限拒绝时停止自动修改并报告
```

常态轮询只读注册表；只有等待就绪或地址变化时做无认证网络探测。不要每 15 秒请求模型，也不要每次轮询都重启服务。重复失败应限次或退避，并留下可定位的失败状态；不能形成快速无限重启循环。

恢复回调必须是目标电脑已核对的本地脚本，日志只记录时间、状态和不含凭据的本机代理地址。后台使用单实例锁，保持隐藏，不打开 Codex/ChatGPT 窗口。当前服务若可能先于监控器启动，应核对其有效代理地址，不能把“监控器当前读到的地址”冒充“服务已经使用的地址”。

本次本机实现使用了已有的专用启动器和恢复入口。**仓库不把这套专用运行目录作为通用安装包发布。** 新电脑由 Skill 依照上述步骤适配已有启动器、实际路径与端口；仅安装 Skill 不会自动注册后台、修改登录项或重启服务。

## 不要再误改窗口自启动

“Codex App 登录后自动打开”与“GPT/Gemini 后台随登录启动”是两项设置。先核对快捷方式的 Target/Arguments、登录项和应用注册，不凭快捷方式名称判断。

- 用户只要窗口不自启：只处理桌面应用的对应入口。没有发现该入口，就说明检查结果，不能改停后台来代替。
- 后台入口应只运行隐藏的后台启动器，不调用 Codex/ChatGPT GUI。
- 不为了关闭窗口启动而停用沙箱服务、系统全局重启应用设置或其他用户程序。
- 回退自动跟随时恢复本机保存的启动项/脚本，只停掉身份明确的监控器，不删除账号或模型。

## 验证与交付口径

2026-09-22 本轮记录：当前代理可达；身份核对后后台重载成功；GPT-5.6 Luna 和 `google-antigravity:gemini-3.8-flash-high` 均通过临时 Codex 后台协议的实际回复测试；本轮原报错桌面任务重发尚待用户确认。

本机自动跟随逻辑已模拟验证“端口不变不动作”“关闭/未就绪不重启”“新端口就绪只恢复一次”“恢复失败后退避、成功后不重复恢复”，并确认隐藏后台在发起工具结束后存活。没有故意切断用户网络，也没有把模拟检查写成真实断网或重新登录后的完整验收。

在新电脑复用时分别验证：网络探测、进程身份保护、后台健康、两款模型真实回复、用户桌面原任务、监控器持续运行，以及授权范围内的代理重连/重新登录。不要把一个层面的成功写成“永久修好”。
